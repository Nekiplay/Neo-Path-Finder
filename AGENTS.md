# AGENTS.md — PathFinder для Minecraft Java Edition 26.2
# (vanilla-exact physics, smooth movement, constants extracted at runtime)

## 1. Роль и цель агента

Ты — AI-агент, который пишет PathFinder для Minecraft Java Edition **26.2**. PathFinder должен:
- находить путь до цели;
- исполнять движение **плавно** (без рывков и телепортаций);
- быть **максимально точным**: предсказанное положение игрока каждый тик должно совпадать с ванильным с точностью до бита.

**Главное правило:** никакие физические константы (гравитация, drag, трение, ускорение) не должны быть захардкожены. Агент обязан **извлекать их из необфусцированного кода игры 26.2** во время выполнения или на этапе инициализации.

---

## 2. Целевая версия и среда

- **Версия игры:** Minecraft Java Edition 26.2 (Chaos Cubed, июнь 2026).
- **Тиковая частота:** 20 тиков/с (1 тик = 50 мс).
- **Язык реализации:** Java (мод/плагин) или JavaScript/TypeScript (Mineflayer-подобный бот).
- **Доступ к коду:** Начиная с 26.1, Mojang поставляет **необфусцированные** JAR-файлы с оригинальными именами классов, методов и полей. Это означает, что рефлексия и прямой доступ к полям `LivingEntity`, `Entity`, `Block` и т.д. работают без маппингов. Для декомпиляции в читаемый исходный код используйте CFR или Fernflower.

## 3. Архитектура PathFinder

PathFinder состоит из трёх слоёв. Каждый слой тестируется независимо.

### 3.1. Physics Core (детерминированный тиковый симулятор)

Чистая функция:
`next_state(state, input) -> state'`

где `state` содержит `position`, `velocity`, `on_ground`, `fall_distance`, `in_water`, `in_lava`, `friction_modifier`; `input` — намерение игрока (`forward`, `strafe`, `jump`, `sneak`, `sprint`, `fly`).

**Порядок операций одного тика должен соответствовать ванильному `LivingEntity.travel()` / `Entity.move()`.** Агент обязан декомпилировать класс `LivingEntity` (и при необходимости `Entity`, `Player`) и восстановить точную последовательность вызовов, а не «угадывать» её по вики.

Типичный (но подлежащий проверке по коду 26.2) порядок для сущности в воздухе:

    position += velocity;
    velocity.y -= gravity;      // gravity извлекается из кода, не хардкодится
    velocity.x *= dragXZ;       // dragXZ извлекается из кода
    velocity.y *= dragY;        // dragY извлекается из кода
    velocity.z *= dragXZ;

Для сущности на земле drag применяется **после** движения и с учётом `slipperiness` блока под ногами. Агент должен найти в декомпилированном коде `LivingEntity.travel` вызов, отвечающий за трение, и извлечь используемые там константы.

### 3.2. A* / Path Search

- Алгоритм: **A\*** по позициям ног (feet block positions), как в Baritone.
- Стоимость ребра: **тики**, измеренные Physics Core. Никаких «эвристических метров».
- Допустимые движения (Moves): walk, sprint, sneak, jump, jump-down, diagonal, swim, climb, parkour, elytra (если разрешено).
- Для прыжков стоимость должна включать полную тиковую симуляцию: разбег, отрыв, полёт, приземление. Агент должен вычислять её из Physics Core, а не брать из таблиц Baritone (они могут быть устаревшими для 26.2).
- Эвристика: допустимая и консистентная. Y-эвристика вычисляется через Physics Core (стоимость спуска на 1 блок в тиках).

### 3.3. Controller / Follower (плавное исполнение)

- На каждом игровом тике контроллер получает текущее состояние, пересчитывает следующий `input` и отправляет его.
- **Запрещено** телепортировать игрока к следующей точке пути. Движение должно быть непрерывным.
- Контроллер должен компенсировать небольшое расхождение (пинг, knockback), перепланируя путь при отклонении > 0.05 блока от предсказанной траектории.
- Повороты камеры (yaw/pitch) — плавные, не более ~30° за тик.

## 4. Извлечение физических констант из кода 26.2 (обязательный этап)

Агент **не имеет права** записывать в код числа вроде `0.08`, `0.91`, `0.98`, `0.546`, `0.42` и т.п. Вместо этого он должен:

### 4.1. Получить необфусцированный JAR
С 26.1 клиентский и серверный JAR-файлы поставляются без обфускации и содержат оригинальные имена полей и методов. Достаточно поместить JAR в classpath проекта.

### 4.2. Декомпилировать целевые классы
Использовать CFR или Fernflower для получения читаемого исходного кода классов:
- `net.minecraft.world.entity.LivingEntity` (метод `travel`)
- `net.minecraft.world.entity.Entity` (метод `move`)
- `net.minecraft.world.level.block.Block` (свойство `slipperiness` / `friction`)
- `net.minecraft.world.entity.ai.attributes.Attributes` (атрибут `MOVEMENT_SPEED`)

### 4.3. Извлечь значения через рефлексию (runtime)
Так как имена не обфусцированы, можно напрямую обращаться к полям и методам. Пример подхода:

```java
// Псевдокод — агент должен адаптировать под реальную структуру 26.2
Class<?> livingEntityClass = Class.forName("net.minecraft.world.entity.LivingEntity");
Field gravityField = livingEntityClass.getDeclaredField("GRAVITY"); // имя проверить в декомпиляции
gravityField.setAccessible(true);
double gravity = gravityField.getDouble(null); // или из экземпляра
```

Если поле `private final`, используйте `AccessWidener` (Fabric) или рефлексию с `setAccessible(true)`. Access widening позволяет легально открыть приватные поля для чтения и записи.

### 4.4. Предпочтительный вариант: извлечение из экземпляра
Многие константы проще получить не из статических полей, а из поведения:
- **Трение блока** — вызвать `block.getFriction()` (или аналог) для конкретного `BlockState`.
- **Гравитация** — прочитать поле у экземпляра `LivingEntity` или найти константу в `Entity`/`LivingEntity`.
- **Drag** — найти поля, используемые в `travel`, и прочитать их значения.

Агент должен **задокументировать** в README, из какого класса и поля взята каждая константа, и приложить фрагмент декомпилированного кода как доказательство.

### 4.5. Кэширование
Извлечённые значения кэшируются после первого чтения, чтобы не вызывать рефлексию каждый тик. При обновлении версии игры кэш сбрасывается и значения перечитываются.

## 5. Требования к плавности (smoothness constraints)

1. **Никаких скачков позиции.** Максимальное перемещение за тик не должно превышать `0.5` блока по горизонтали и `0.5` блока по вертикали (если это не падение). Если Physics Core предсказывает больше — это баг в порядке drag или в извлечённых константах.
2. **Без «дрожания» на месте.** Если целевая точка достигнута, контроллер обнуляет input. Порог обнуления скорости (обычно `0.003`) также должен быть извлечён из кода, а не захардкожен.
3. **Повороты камеры** — не более 30°/тик. Резкий поворот на 180° за один тик ломает `moveRelative`.
4. **Перепланирование** при отклонении > 0.05 блока.
5. **Плавный старт и стоп:** не подавать `sprint=true`, если до препятствия меньше 2 блоков.

## 6. Верификация и тесты (definition of done)

Агент не считается выполнившим задачу, пока не проходят следующие тесты:

1. **Oracle-тест:** Physics Core прогоняется headless против реального ванильного клиента 26.2 (или декомпилированного `LivingEntity.travel`) на одинаковых inputs; позиция и скорость совпадают **побитово** (double-to-double) на протяжении не менее 200 тиков.
2. **Тест на трение:** ходьба по обычному блоку 100 тиков без препятствий → скорость выходит на терминальную, предсказанную Physics Core. Значение терминальной скорости **не хардкодится**, а вычисляется из извлечённых констант.
3. **Тест на лёд:** разгон на льду должен соответствовать поведению, предсказанному Physics Core с учётом `slipperiness` блока, извлечённого из кода.
4. **Тест на прыжок:** прыжок с места на 1 блок вверх → приземление ровно на Y+1, без «зависания» и без двойного прыжка.
5. **Тест на воду:** погружение и всплытие без телепортаций, `on_ground` корректен.
6. **Тест пути:** для 10 случайных пар точек в регионе 16×16×8 стоимость пути в тиках не более чем на 5% отличается от оптимальной, найденной полным перебором Physics Core.

## 7. Запреты (anti-patterns)

- ❌ Записывать в код любые физические константы (`0.08`, `0.91`, `0.98`, `0.546`, `0.42` и т.п.). Все они должны быть извлечены из кода 26.2.
- ❌ Использовать `0.91` как трение на земле. Это drag для воздуха. Трение на земле берётся из `slipperiness` блока.
- ❌ Хардкодить скорость 4.317 м/с или 5.612 м/с как «скорость движения». Это терминальные скорости, а не константы ускорения; они вычисляются.
- ❌ Применять трение до перемещения. В ваниле — после (проверить по декомпилированному `travel`).
- ❌ Игнорировать `friction_modifier` / атрибут скорости в 26.2.
- ❌ Телепортировать игрока к waypoint.
- ❌ Использовать эвристику A* в «метрах» или «блоках» без перевода в тики через Physics Core.
